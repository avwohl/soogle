soogle — open work
==================

Written 2026-08-22, after fixing GitHub issue #1 (Monticello listings were
indexed once per version instead of once per package).


1. Descriptions from version messages
-------------------------------------
The remaining half of issue #1, and the only substantive item here.

Descriptions today state facts about the listing:

    Monticello package 'ToolsTests' in the trunk repository at
    source.squeak.org. Latest ToolsTests-ct.137.mcz; 134 versions.

True, and better than the repository blurb that used to be copied onto every
package, but it does not say what the package *is*. Monticello has no
per-package description; the closest thing that genuinely belongs to a
package is the commit message on its newest version, which is what
LinqLover pointed at in the issue.

Getting it means fetching and unzipping each .mcz to read its version info.
That is a scraper of a different shape from the listing walk — network-heavy,
needs caching so a rescrape does not refetch thousands of archives — so it is
its own piece of work rather than a tweak to scrape/monticello.py.

The weekly job (/etc/crontab -> periodic.sh -> weekly.d/30-soogle.sh ->

3. The web app has no tests
---------------------------
web/search/tests.py is an empty stub — `manage.py test` reports 0 tests.

On 2026-08-22 the site returned 500 for about five minutes because
settings.py raised during import: it had been loading .env through
python-dotenv, which is not importable by the mod_wsgi daemon user, inside a
try/except ImportError that hid the failure. Any smoke test that imported the
settings module and fetched one page would have caught it before deploy.

The scrape side has tests/test_monticello.py (26 checks, no framework, run
with `python3 tests/test_monticello.py`). The web side has nothing.

5. The other scrapers have not been audited
-------------------------------------------
Issue #1 was a per-version identity bug in the two scrapers that walk
Monticello .mcz listings. Both are fixed. The others were checked only for
that same defect, and do not have it — SmalltalkHub keys on owner/name,
SqueakMap on a UUID, neither one per file.

That is not the same as having reviewed them for correctness. Nobody has
looked at whether SqueakMap, SmalltalkHub, SourceForge, Launchpad or the
GitHub scraper have identity or metadata bugs of their own kind.


6. GitHub repos created 2026-06-15 .. 2026-08-06 were never scraped -- done
-----------------------------------------------------------------------------
Written 2026-09-28, and done the same day.

`github --incremental` searches `created:` over the last 30 days only
(scrape/github.py) and ignores job history.  It got 401 on every run from
2026-06-21 (job 182) to 2026-09-06, because a dead GH_TOKEN in .env overrode
the live one from ~/.bashrc, and it failed again on 09-20 and 09-27 after
the token was rotated a second time.  Until 161f45a those failures still
reported "periodic: ok".  (That commit's message says the failures began
"at least 2026-08-09" and that the dead .env line was gone; the first 401
was 06-21, and a GH_TOKEN line was put back into .env a minute after the
fix.  daily.bash and weekly.bash now load .env through load_env.bash, where
the login environment wins, so a stale .env copy can no longer do this.)

That left a hole: 207 Smalltalk repos created 06-15 .. 08-06, none in
scrape_raw.  `github --since YYYY-MM-DD` now searches from a given date, and
job 355 (`--since 2026-06-15`) found 400, saved 278 with 0 errors.  159 of
the 207 are stored now, plus 46 of the 64 created since 09-14; the rest were
filtered as not Smalltalk.  process and llm-review ran after it: 106 new
packages reviewed, 66 kept, 40 blocked.  Use --since again whenever the
incremental run has been broken for more than 30 days.


7. Three weekly phases still cannot fail the run
------------------------------------------------
Written 2026-09-28.

cmd_submissions, cmd_discover and cmd_youtube (scrape/__main__.py) print
errors=N and return 0, and the SerpAPI calls in scrape/web.py and
scrape/youtube.py catch every request error, log a WARNING and return no
results.  An expired or exhausted SERPAPI_KEY therefore reports
"periodic: ok".  The 2026-07-05 run did exactly this: all ten discovery
queries timed out, `found=0 errors=0`, ok.  weekly.bash's phase_failed can
only fire for them on an uncaught exception.  Fix: `if result["errors"]:
sys.exit(1)` like the other handlers, and count a failed SerpAPI request as
an error.
